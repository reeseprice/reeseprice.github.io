Task 01 · Linux Fundamentals
Bootable Linux USB with dd
// create · verify · boot
What you need to execute
→
Write a Linux ISO to a USB drive using dd with the correct flags — if, of, bs, status
→
Identify the correct device path (/dev/sdX) using lsblk or fdisk — never guess this
→
Flush the write buffer with sync before unplugging
→
Boot the machine from USB and verify the live environment loads
→
Explain what each flag does if asked — no black-box memorization
Critical: The of= target in dd will be completely overwritten with zero recovery. Always confirm the device path with lsblk first. Writing to your main drive instead of the USB is unrecoverable data loss.
Step 1 — identify your USB device
terminal
# Run BEFORE inserting USB, then again AFTER — new entry = your USB
lsblk

# Or with more detail:
sudo fdisk -l

# Confirm the device — look for your USB size (e.g. 32G)
# It will appear as /dev/sdb or /dev/sdc — NEVER /dev/sda (that's your main drive)
Step 2 — write the ISO with dd
terminal — the full command
sudo dd if=/path/to/ubuntu.iso \
         of=/dev/sdX \
         bs=4M \
         status=progress \
  && sync

# Flag breakdown:
#   if=   input file  — your ISO source
#   of=   output file — your USB device (replace X with b, c, etc.)
#   bs=   block size  — 4M is optimal for USB writes (4 megabytes per chunk)
#   status=progress   — shows transfer speed and progress live
#   sync  — flushes kernel write buffer — DON'T skip this
Step 3 — verify and boot
verification commands
# Verify the write completed without errors
sudo dd if=/dev/sdX bs=4M count=100 | md5sum
sudo dd if=/path/to/ubuntu.iso bs=4M count=100 | md5sum
# Hashes should match

# Then reboot and enter BIOS/UEFI (usually F12, F2, or Del at startup)
# Select USB as boot device → Ubuntu live environment should load
Self-check quiz
What does bs=4M do, and what happens if you omit it? ▾
bs=4M sets the block size to 4 megabytes — dd reads and writes 4MB at a time. This significantly speeds up the transfer compared to the default 512-byte block size. Omitting it doesn't cause an error, but the write will be dramatically slower (potentially 10–20× slower on large ISOs). Always include it.
Why must you run sync after dd completes? ▾
dd writes to the kernel's write buffer — not directly to the USB hardware. When dd exits, data may still be in memory waiting to be flushed. sync forces the kernel to write all buffered data to the physical device. If you unplug before sync completes, the USB may be corrupt and unbootable.
How do you find which device is your USB without guessing? ▾
Run lsblk before and after inserting the USB. The new entry that appears is your device. Cross-reference the size (e.g., 32G) to confirm. The root disk is almost always /dev/sda — your USB will be /dev/sdb or later. Never use /dev/sda as the of= target.

Task 02 · Networking
WireGuard VPN via CLI
// keygen · config · connect · verify
What you need to execute
→
Generate a WireGuard private/public keypair using wg genkey and wg pubkey
→
Write a valid wg0.conf configuration file by hand — Interface and Peer sections
→
Bring the tunnel up with wg-quick up wg0 and verify with wg show
→
Bring the tunnel down cleanly with wg-quick down wg0
→
Explain the difference between a WireGuard private key, public key, and preshared key
Step 1 — install WireGuard
terminal
sudo apt update && sudo apt install wireguard -y

# Verify install
wg --version
Step 2 — generate keypair
terminal — key generation
# Generate private key (keep this secret — never share it)
wg genkey | sudo tee /etc/wireguard/privatekey

# Derive public key from private key
sudo cat /etc/wireguard/privatekey | wg pubkey | \
  sudo tee /etc/wireguard/publickey

# Lock down permissions on private key
sudo chmod 600 /etc/wireguard/privatekey

# View your keys
sudo cat /etc/wireguard/privatekey
sudo cat /etc/wireguard/publickey
Step 3 — write the config file
/etc/wireguard/wg0.conf — structure
# Create config file
sudo nano /etc/wireguard/wg0.conf

# ── Paste this structure (fill in real values) ──

[Interface]
# This machine's VPN IP address
Address = 10.0.0.2/24

# Your private key (from /etc/wireguard/privatekey)
PrivateKey = <YOUR_PRIVATE_KEY>

# Optional: DNS to use inside the tunnel
DNS = 1.1.1.1

[Peer]
# The VPN server's public key
PublicKey = <SERVER_PUBLIC_KEY>

# Route ALL traffic through the VPN (0.0.0.0/0) or just the VPN subnet
AllowedIPs = 0.0.0.0/0

# Server's public IP and WireGuard port
Endpoint = <SERVER_IP>:51820

# Keep connection alive through NAT (send keepalive every 25 seconds)
PersistentKeepalive = 25
Step 4 — bring up, verify, bring down
terminal — connect and verify
# Bring tunnel up
sudo wg-quick up wg0

# Verify tunnel is active — shows peers, latest handshake, traffic
sudo wg show

# Confirm your IP inside the VPN
ip addr show wg0

# Test connectivity through the tunnel
ping 10.0.0.1    # ping the server's VPN IP

# Bring tunnel down cleanly
sudo wg-quick down wg0

# Enable on boot (optional)
sudo systemctl enable wg-quick@wg0
Self-check quiz
What is the relationship between a WireGuard private key and public key? ▾
The private key is generated randomly and must be kept secret — it never leaves your machine. The public key is mathematically derived from the private key using Curve25519 elliptic-curve cryptography. You share the public key with the server (peer) so it can authenticate you. Even with your public key, no one can derive your private key.
What does AllowedIPs = 0.0.0.0/0 mean vs 10.0.0.0/24? ▾
0.0.0.0/0 routes ALL traffic through the VPN tunnel — full tunnel mode. Every packet leaving your machine goes through the VPN. 10.0.0.0/24 is split tunneling — only traffic destined for the 10.0.0.x subnet goes through the tunnel; everything else goes directly to the internet. For an interview environment, you'll likely be given a specific config specifying which mode to use.
The tunnel comes up but you can't ping the server. What do you check first? ▾
1. sudo wg show — check if a handshake has occurred (latest handshake timestamp). No handshake = the server isn't responding. 2. Check the Endpoint IP/port is correct. 3. Check the server's public key in your config matches what the server expects. 4. Check that UDP port 51820 is open on the server firewall. 5. Confirm your private key matches the public key you gave the server.

Task 03 · Remote Access
SSH with Private Key Authentication
// keygen · copy · connect · harden
What you need to execute
→
Generate an SSH keypair with ssh-keygen using Ed25519 (preferred) or RSA-4096
→
Copy the public key to a server using ssh-copy-id or manual authorized_keys entry
→
Connect to a server using ssh -i specifying the private key explicitly
→
Use an SSH config file (~/.ssh/config) to simplify repeated connections
→
Explain why key-based auth is more secure than password auth
Step 1 — generate SSH keypair
terminal — keygen
# Ed25519 — recommended (shorter key, stronger security than RSA)
ssh-keygen -t ed25519 -C "your-email@example.com"
# Accept default path (~/.ssh/id_ed25519) or specify custom path
# Add a passphrase (recommended) or leave blank

# RSA alternative (use if server only supports RSA)
ssh-keygen -t rsa -b 4096 -C "your-email@example.com"

# Keys are saved at:
#   Private: ~/.ssh/id_ed25519   (NEVER share this)
#   Public:  ~/.ssh/id_ed25519.pub  (share this freely)

# View your public key
cat ~/.ssh/id_ed25519.pub
Step 2 — copy public key to server
terminal — authorize your key
# Method 1: ssh-copy-id (easiest — requires password auth to be enabled)
ssh-copy-id -i ~/.ssh/id_ed25519.pub user@server-ip

# Method 2: Manual — if ssh-copy-id isn't available
cat ~/.ssh/id_ed25519.pub | ssh user@server-ip \
  "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"

# Verify it was added
ssh user@server-ip "cat ~/.ssh/authorized_keys"
Step 3 — connect with private key
terminal — SSH connection
# Basic connection specifying key explicitly
ssh -i ~/.ssh/id_ed25519 user@server-ip

# With custom port
ssh -i ~/.ssh/id_ed25519 -p 2222 user@server-ip

# Verbose mode — useful for debugging connection failures
ssh -vvv -i ~/.ssh/id_ed25519 user@server-ip

# ── SSH Config file — cleaner approach ──────────────
# Edit: nano ~/.ssh/config

Host anduril-server
    HostName 10.0.0.1           # VPN IP after WireGuard connects
    User ubuntu
    IdentityFile ~/.ssh/id_ed25519
    Port 22

# Then connect simply with:
ssh anduril-server
Self-check quiz
Why is key-based auth more secure than password auth? ▾
Passwords can be brute-forced, phished, or leaked. SSH keys use asymmetric cryptography — the private key proves identity without ever being transmitted over the network. Even if someone intercepts the connection, they get nothing useful. A 256-bit Ed25519 key has more entropy than any human-chosen password and can't be guessed. Most server hardening practices disable password auth entirely and require keys.
You try to SSH in and get "Permission denied (publickey)". Walk through your debug steps. ▾
1. Run ssh -vvv user@host — verbose output shows exactly which keys were offered and why auth failed. 2. Check that your public key is in the server's ~/.ssh/authorized_keys. 3. Check file permissions: ~/.ssh/ must be 700, authorized_keys must be 600 — wrong permissions cause SSH to ignore the file. 4. Confirm you're using the right private key with -i. 5. Check that the username matches an account on the server.
What's the difference between ~/.ssh/id_ed25519 and ~/.ssh/id_ed25519.pub? ▾
The file without .pub is your private key — it stays on your machine, permissions 600, never shared. The .pub file is your public key — this is what you copy to servers via authorized_keys. The public key is safe to share. The private key authenticates you by proving you hold the matching key — the server encrypts a challenge with your public key, and only your private key can decrypt it.

Task 04 · File Transfer
SCP — Secure File Transfer
// copy · pull config · verify
What you need to execute
→
Use scp to copy a file from a remote server to your local machine (pull)
→
Use scp to push a file from local to remote
→
Specify a private key with -i and a custom port with -P
→
Pull a WireGuard config file (.conf) from the server into your bootable Linux environment
→
Verify the transferred file contents with cat and md5sum
SCP syntax — all patterns
terminal — scp command patterns
# ── PULL: remote → local ────────────────────────────

# Basic pull
scp user@server-ip:/remote/path/file.conf /local/destination/

# With private key specified
scp -i ~/.ssh/id_ed25519 user@10.0.0.1:/etc/wireguard/client.conf ~/

# With custom port (-P is UPPERCASE for scp, unlike ssh's -p)
scp -P 2222 -i ~/.ssh/id_ed25519 user@server:/path/file ./

# Pull entire directory recursively
scp -r user@server:/remote/dir/ /local/dir/

# ── PUSH: local → remote ────────────────────────────

scp -i ~/.ssh/id_ed25519 /local/file.txt user@server:/remote/destination/

# ── VERIFY after transfer ───────────────────────────

cat ~/client.conf              # read the file
md5sum ~/client.conf           # verify integrity
wc -l ~/client.conf           # count lines (sanity check)
The interview scenario — end-to-end
interview task sequence
# You will be asked to:
# 1. Boot a Linux USB  2. Connect WireGuard  3. SSH in  4. SCP a config file

# ── Step 1: boot into live Ubuntu from USB ──────────
# (done at BIOS level — select USB boot device)

# ── Step 2: connect WireGuard using provided config ─
sudo wg-quick up /path/to/provided.conf
sudo wg show   # verify handshake

# ── Step 3: SSH into server over VPN ────────────────
ssh -i ~/.ssh/id_ed25519 user@10.0.0.1

# ── Step 4: SCP another WireGuard config from server ─
scp -i ~/.ssh/id_ed25519 \
    user@10.0.0.1:/etc/wireguard/new-client.conf \
    ~/new-client.conf

# Verify it arrived correctly
cat ~/new-client.conf

# Done. All 4 tasks complete.
Self-check quiz
scp -P vs ssh -p — why the difference in case? ▾
It's a historical quirk. In ssh, -p (lowercase) sets the port. In scp, -P (uppercase) sets the port because -p was already taken to mean "preserve file attributes" (timestamps, permissions). This trips people up often. When in doubt: scp uses uppercase -P for port.
You SCP a WireGuard config file and want to use it immediately. What's the next command? ▾
First verify the file looks right with cat ~/new-client.conf. Then bring down any existing WireGuard tunnel: sudo wg-quick down wg0. Then bring up the new config: sudo wg-quick up ~/new-client.conf (you can pass a path directly instead of an interface name). Then verify: sudo wg show.
What's the difference between scp and rsync for this use case? ▾
scp is a simple, one-shot secure copy over SSH — good for transferring individual files quickly. rsync is smarter: it only transfers the differences (delta sync), handles large files more efficiently, and is better for directories. For a single config file in an interview, scp is the right tool — it's simpler and faster to type. Use rsync for backups and large-scale transfers.

Final prep quiz
You're in a live Ubuntu USB environment and need to connect WireGuard. WireGuard isn't installed. What do you do? ▾
First check if you have internet: ping 8.8.8.8. If yes: sudo apt update && sudo apt install wireguard -y. If no internet before the VPN is up: you may need to use an offline package or the interviewer will provide the config for an already-configured tunnel. Ask clarifying questions — "is WireGuard pre-installed on the live environment?" is a reasonable question before starting.
The interviewer gives you a .conf file on a USB stick. How do you use it with wg-quick? ▾
Mount the USB: sudo mount /dev/sdX1 /mnt. Copy the config: sudo cp /mnt/client.conf /etc/wireguard/wg0.conf. Set permissions: sudo chmod 600 /etc/wireguard/wg0.conf. Then: sudo wg-quick up wg0. Or pass the path directly: sudo wg-quick up /mnt/client.conf — wg-quick accepts both interface names and file paths.
Why do all four of these tasks connect to each other in the interview context? ▾
They form a complete secure access chain. The bootable USB gives you a clean, controlled Linux environment. WireGuard gets you onto the private network. SSH with key auth gets you into the specific server securely without a password. SCP transfers the config file you need — which might be a new WireGuard config to bring up a different tunnel. Each task depends on the previous one working correctly. That's the point of the interview: can you build a secure remote access pipeline from scratch?
